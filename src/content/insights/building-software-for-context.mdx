The gap between how software is designed and how it is actually used in the field is often wider
than developers expect. Bridging it requires more than good UX.

A tool that assumes constant connectivity, a clean office environment, or an operator with time to
learn a complex workflow will quietly fail in contexts where none of those assumptions hold. When I
design for schools, clinics and marketplaces, the constraints of the environment shape the feature
set more than any competitive analysis does.

## The cost of ignoring context

Every feature added to a system is also an assumption made about the world it will operate in. When
those assumptions are wrong, the software does not just feel awkward â€” it stops being used.
Adoption silently collapses back to spreadsheets, paper and WhatsApp messages, which were exactly
the channels the software was supposed to replace.

## What I try to do instead

1. Start from the operational reality â€” not the ideal workflow.
2. Build the reliable core first: data, payments, records.
3. Reduce the number of assumptions required for the system to work.
4. Design interfaces for the least expert, least patient user who depends on the outcome.
